# KnowFlow 简历与面试讲解稿

> 更新日期：2026-10-23

## 1. 简历项目经历

### KnowFlow：轻量级多模态 RAG 知识库问答系统

**技术栈：** Python、FastAPI、LightRAG、Ollama、BM25、向量检索、RRF

**项目背景：** 针对传统文本 RAG 难以统一处理 PDF 中的表格、图片和公式，以及检索效果缺少可量化评估的问题，基于 RAG-Anything 与 LightRAG 二次开发轻量级多模态知识库，打通文档解析、知识入库、混合检索、引用回答和 Web 交互流程。

**项目亮点：**

- 搭建多模态 RAG 全流程，支持 PDF、Markdown、PNG/JPG 文档中的文本、表格、图片和公式解析，使用 FastAPI 封装文件上传、异步任务状态和问答接口，并提供 Streamlit 可视化页面。
- 实现 BM25、BGE-M3 稠密向量检索及 RRF 融合策略；在 12 文档、120 题闭集评测集上，混合检索 MRR 达 **98.06%**、Recall@5 达 **99.58%**。
- 建立覆盖文本、表格、图像语义、公式、跨文档和拒答场景的分层评测体系，自动统计 Recall、Precision、MRR、nDCG、回答准确率、引用质量、时延和 Token 消耗。
- 使用真实模型 API 完成 RAG 与无 RAG 的 240 次配对生成实验，回答准确率由 **16.67% 提升至 99.17%**，绝对提升 **82.5 个百分点**；引用召回率达到 **99.58%**，拒答题幻觉率为 **0%**。

### 精简版

如果简历空间有限，可使用下面三条：

- 基于 RAG-Anything、LightRAG 和 FastAPI 开发轻量级多模态知识库，支持 PDF、Markdown、图片中的文本、表格、图像语义和公式解析、索引及问答。
- 实现 BM25、BGE-M3 向量检索与 RRF 融合，在 120 题闭集评测集上取得 **98.06% MRR** 和 **99.58% Recall@5**。
- 完成 RAG/no-RAG 真实 API 对照实验，准确率从 **16.67% 提升至 99.17%**，并建立引用质量、拒答、时延和 Token 消耗等可复现实验指标。

## 2. 指标表述边界

简历数字必须带上实验范围，推荐表述为“在 12 文档、120 题合成闭集评测集上”，不要写成“系统通用准确率 99.17%”。

需要主动说明以下边界：

- 本轮“图像”问题评测的是文档解析后的图像语义证据，不等价于公开视觉问答基准。
- 99.17% 来自预标注关键词规则，不代表人工主观质量评分。
- 数据集包含明确的项目名和编号，词法特征较强，因此 BM25 Recall@5 达到 100%。
- RAG 与 no-RAG 请求并发执行，不能根据本轮时延直接声称 RAG 更快。
- 拒答基线被明确告知没有外部资料，其 0% 幻觉率属于受控提示下的结果。

## 4. 三至五分钟面试讲解

### 0:00～0:40：项目背景

传统文本 RAG 通常只处理连续文本，PDF 中的表格、架构图和公式容易在解析或切分阶段丢失。我希望做的不是一个只展示聊天页面的 Demo，而是一个具备文档上传、异步处理、混合检索、引用回答和可复现实验的完整项目。

### 0:40～1:30：系统链路

用户通过 Streamlit 上传 PDF、Markdown 或图片，FastAPI 完成扩展名、文件签名、大小和安全文件名校验，再创建后台处理任务。MinerU 将文档拆分为文本、表格、图片和公式块，RAG-Anything 将多模态内容转换为可检索语义，LightRAG 负责向量与图关系存储。查询阶段检索相关证据，再由模型依据证据生成回答和引用。

### 1:30～2:20：工程设计

服务生命周期只维护一个 RAG 实例；关闭服务时先等待活动任务，再释放存储。文档解析使用容量为 1 的信号量避免本地解析资源竞争，查询并发数可配置。上传、任务和查询异常被映射为稳定错误码及请求 ID，避免把密钥、本地路径和异常栈返回给客户端。当前任务状态保存在内存中，因此项目明确采用单 worker 部署。

### 2:20～3:30：检索实验

我构建了 12 份档案、48 个证据块和 120 道问题，覆盖文本、表格、图像语义、公式、跨文档与拒答六类场景，三档难度各 40 题。检索部分对比 BM25、BGE-M3 dense 和 RRF hybrid。Hybrid 的 Precision@1 为 96.67%、MRR 为 98.06%、Recall@5 为 99.58%。BM25 的 Recall@5 反而达到 100%，说明数据中的项目代号和传感器编号给词法检索提供了明显优势，这也是实验必须披露的偏差。

### 3:30～4:20：生成实验与错误分析

生成部分对 Hybrid RAG 和 no-RAG 各执行 120 次真实 API 请求。RAG 正确 119 题，准确率 99.17%；no-RAG 正确 20 题，准确率 16.67%，而且正确项全部是拒答题。绝对提升为 82.5 个百分点，McNemar 精确检验结果约为 `3.16e-30`。唯一错误是一个跨文档问题：Top-5 找到了第一个项目的图像证据，却漏掉第二个项目的表格证据，说明瓶颈位于多跳检索而非答案生成。

### 4:20～5:00：取舍与后续

当前系统是单机 MVP，不把本地文件存储和内存任务状态包装成生产架构。后续优先方向是查询拆分、多跳检索和 reranker，并使用公开多模态数据集、OCR 扰动和同义改写扩大实验；工程侧再考虑 Redis、任务队列、外部向量库和多 worker 部署。

## 5. 常见面试问题

### 为什么不从零实现 RAG？

项目目标是多模态 RAG 的应用工程化和效果评测。RAG-Anything 已提供多模态解析与 LightRAG 集成，我把主要精力放在安全上传、生命周期、并发控制、HTTP/UI、检索消融和可复现实验上。这样既复用了成熟组件，也保留了明确的二次开发工作。

### 你的二次开发具体做了什么？

主要包括四部分：封装可运行的 FastAPI 与 Streamlit 应用；补充上传安全、任务状态、并发和错误处理；实现 BM25、BGE-M3 与 RRF 实验检索链路；建设带证据真值的数据集和自动评测脚本，输出 JSON/CSV 逐题记录与统计结果。

### 为什么同时使用 BM25 和向量检索？

BM25 擅长项目名、编号和专有名词等精确匹配，向量检索更适合同义表达和语义相近问题。RRF 不依赖两种检索分数处于同一尺度，通过名次倒数融合结果。本轮 Hybrid 的 MRR 和 nDCG@5 最好，但 BM25 的 Recall@5 更高，因此不能简单得出“混合检索所有指标都更好”的结论。

### RRF 是如何工作的？

对每个检索器返回的排名，按 `1 / (k + rank)` 计算贡献，再对同一证据的贡献求和并重新排序。项目使用固定的 `k=60`，避免直接混合 BM25 分数与余弦相似度。

### 图片如何进入知识库？

MinerU 输出图片块及其上下文，视觉模型生成可检索的语义描述，RAG-Anything 再将描述及相关实体、关系写入存储。当前检索主要针对图片的语义表示，而不是直接对原始像素做相似度搜索。

### 如何定义“正确回答”？

每道题预先标注参考答案、必须命中的关键词和证据 ID。生成后使用确定性规则判分，公式比较会忽略空白；拒答题必须明确表示资料未提供。这种方式便于回归和复现，但不能完全替代人工评价或校准后的 LLM-as-Judge。

### 如何衡量检索效果？

使用 Recall@1/3/5 衡量相关证据是否被召回，Precision@K 衡量上下文噪声，MRR 关注第一个相关证据出现的位置，nDCG 衡量整体排序质量。跨文档问题有两个证据真值，因此能暴露“只找回其中一跳”的问题。

### 为什么 Recall@5 很高，回答仍然会错？

Recall@5 是所有问题的平均值，99.58% 仍允许个别证据漏召回。唯一错误恰好是跨文档问题缺少第二个证据；生成模型只能依据拿到的上下文作答，因此检索阶段的单点漏召回会传导到最终答案。

### 引用精确率为什么只有 88.61%？

引用召回率为 99.58%，说明正确证据基本都被引用；精确率较低是因为模型有时把 Top-5 中的辅助证据也列入引用。改进方向包括缩小上下文、加入 reranker，并要求模型只引用直接支持答案的证据。

### 如何保证实验可复现？

数据集由确定性脚本生成并记录 SHA-256；模型温度固定为 0；检索参数、模型名和统计规则写入结果文件；每个问题保留检索排名、回答、引用、时延和 Token；执行过程中逐请求保存 checkpoint，成功后导出 JSON 与 CSV 工件。

### 为什么只使用一个 Uvicorn worker？

任务状态是进程内字典，LightRAG 使用本地文件存储，多进程会造成任务视图不一致和并发写入风险。单 worker 是明确的 MVP 约束。生产化之前需要先迁移任务状态、锁和存储。

### 如何控制并发和故障影响？

文档解析使用容量为 1 的信号量，查询并发由环境变量控制；接口设置上传大小和参数限制，异常统一映射并脱敏。实验脚本使用有限线程池并逐请求保存 checkpoint，可在网络或 API 异常后继续运行。

### 当前最大的技术限制是什么？

第一，数据集是合成闭集，词法特征明显；第二，图像类问题评测的是解析后的语义块，不包含本轮 OCR/VLM 误差；第三，目前没有查询拆分和 reranker，跨文档检索仍可能只召回一跳；第四，单机存储和内存任务状态无法直接水平扩展。

### 下一步如何继续优化？

算法侧增加查询拆分、多跳检索、cross-encoder reranker 和 Top-K 敏感性实验；数据侧接入公开多模态问答集并加入 OCR 噪声、图片模糊和同义改写；工程侧将任务状态迁移到 Redis、解析任务迁移到任务队列，并接入外部向量数据库。
