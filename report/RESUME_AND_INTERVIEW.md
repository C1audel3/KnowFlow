# KnowFlow 简历与面试讲解稿

> 更新日期：2026-09-17

## 1. 项目名称

**KnowFlow——轻量级多模态 RAG 知识库**

技术栈：Python、FastAPI、Streamlit、RAG-Anything、LightRAG、MinerU、DeepSeek、Ollama、bge-m3、pytest。

## 2. 简历描述

以下四条可以直接放在简历中，根据版面删减：

- 基于 RAG-Anything 与 LightRAG 二次开发轻量级多模态知识库，支持 PDF、Markdown、图片中文本、表格、图片和公式的统一解析、索引与 `mix` 混合检索。
- 使用 FastAPI 封装文档上传、异步任务状态和问答接口，加入文件签名/大小校验、统一错误码、请求 ID、查询并发限制与安全错误脱敏；使用 Streamlit 构建中文演示页面。
- 接入 DeepSeek V4.1 Flash 与本地 Ollama `bge-m3`，使用单进程本地存储完成从真实文档入库到多模态问答的端到端闭环。
- 设计 16 题固定多模态回归集，覆盖文本、表格、图片、公式、跨文档和拒答场景；完成两轮共 32 次真实 HTTP 请求，请求成功率和固定规则命中率均为 100%，全量自动化测试 470 项通过。

不要写成“模型准确率 100%”或“平均响应仅 132 ms”。前者把固定关键词规则扩大成语义准确率，后者忽略了查询缓存。

## 3. 一句话介绍

我基于 RAG-Anything 和 LightRAG 做了一个可上传真实多模态文档、可观察处理状态、可通过网页问答，并且有固定评测数据支撑的单机 RAG 应用。

## 4. 三至五分钟讲解提纲

### 0:00～0:40：背景与目标

传统文本 RAG 容易丢失 PDF 里的表格、架构图和公式。我选择在 RAG-Anything 上二次开发，目标不是重新实现解析器，而是把上游能力封装成一个简单、可演示、可测试的完整应用。

### 0:40～1:40：数据链路

用户通过 Streamlit 上传 PDF、Markdown 或图片。FastAPI 校验扩展名、文件签名、大小和安全文件名，然后创建后台任务。MinerU 把文档拆成文本、图片、表格和公式，RAG-Anything 为多模态内容生成描述，LightRAG 将向量信息和图谱关系写入本地存储。查询固定使用 `mix` 模式，融合局部实体、全局关系和向量块，再由 DeepSeek 生成回答。

### 1:40～2:35：工程设计

服务生命周期中只创建一个 RAG 实例，并在关闭时等待活动文档任务再释放存储。文档解析使用单独信号量串行执行，查询使用可配置信号量限制并发。任务状态保存在内存，适合单 worker 演示。接口异常被映射为稳定错误码和请求 ID，客户端不会看到密钥、本地路径或完整异常栈。

### 2:35～3:30：测试与结果

测试分为默认离线测试和显式开启的真实模型测试。固定评测集有 16 题，覆盖六类场景，并通过真实 HTTP API 执行两轮。结果是 32 次请求全部成功、固定规则全部命中；全量测试 470 项通过。评测文件保存数据集 SHA-256、模型名称、逐题回答和 P50/P95 延迟，因此简历数字可以追溯。

### 3:30～4:30：取舍与后续

项目当前是单机 MVP，没有把内存任务表和本地向量库包装成生产系统。下一步会优先增加结构化引用与引用准确率评测，再把任务状态迁移到 Redis、解析任务迁移到 Celery，最后接外部向量库支持多 worker 和水平扩展。

## 5. 常见面试问题

### 为什么不从零实现 RAG？

项目重点是应用层工程化和评测。RAG-Anything 已解决多模态解析与 LightRAG 集成，我把时间投入到安全上传、生命周期、任务状态、并发控制、HTTP/UI 和可复现评测，避免重复制造底层轮子。

### `mix` 检索有什么作用？

它同时利用实体局部信息、关系全局信息和向量相似内容。对于“负责人是谁”这类实体问题、跨文档关系问题以及普通语义问题，比只做单一路径向量检索更适合当前样例。

### 图片如何进入知识库？

MinerU 输出图片块及上下文，视觉模型生成可检索的语义描述，RAG-Anything 把描述和相关实体、关系写入 LightRAG。查询不是直接对图片像素做向量搜索，而是检索其结构化语义表示；必要时上游还支持 VLM 增强查询。

### 为什么只用一个 Uvicorn worker？

任务状态是进程内字典，LightRAG 使用本地文件存储，多进程会产生状态不一致和并发写入风险。单 worker 是明确的 MVP 约束。生产化需要先迁移任务状态、锁和存储，再增加 worker。

### 如何防止模型请求压垮服务？

文档解析使用容量为 1 的信号量；查询并发由 `MAX_QUERY_CONCURRENCY` 控制。接口参数、超时和上传大小也有限制。进一步可加入队列、速率限制、熔断与配额。

### 为什么评测不用“准确率”？

当前自动评测使用关键词、任选关键词和禁用词规则，它适合确定性回归，但不能完整判断事实一致性和表达质量，所以文档统一称“固定规则命中率”。语义准确率需要人工标注、引用核验或经过校准的裁判模型。

### 评测中遇到过什么问题？

一个拒答用例最初把其他传感器的已知数值全部设为禁用词，导致模型正确引用证据时被误判。后来将规则改为只禁止把这些数值错误归给未知的 Sensor-D。这说明评测规则本身也要接受审查，不能只看最终百分比。

### 缓存对性能数字有什么影响？

LightRAG 会缓存关键词提取和最终回答。提交结果中的约 132 ms 是重复问题命中缓存的延迟；阶段 4 的一个未缓存问题耗时约 14.6 秒。简历不把缓存延迟包装成首次生成性能。

### 当前最大的技术限制是什么？

结构化来源字段仍可能为空，因此还无法评估引用准确率。这比继续扩大关键词题库更值得优先解决，因为可追溯证据是 RAG 与普通聊天模型的重要区别。

## 6. 演示顺序

1. 展示 README 架构图与项目结果。
2. 打开 Streamlit，确认 API 与 RAG 已就绪。
3. 上传 `data/samples/phase2_multimodal.pdf`，展示任务状态和内容类型统计。
4. 依次询问正文、表格、图片、公式问题。
5. 询问一个资料未提供的问题，展示拒答。
6. 打开 `report/artifacts/phase5_results.json`，说明评测结果可追溯。
7. 最后说明单 worker、空来源字段和生产化路线，主动给出边界。
